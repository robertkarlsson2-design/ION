
# Writing Ion for Lightning Web Components (LWC)

The LWC emitter (`emitters/lwc/emit.ts`) produces a **structured 4-file output** for a single Lightning Web Component:

```
LwcOutput {
  html: string,   // <template>...</template>
  js:   string,   // class extending LightningElement
  css:  string,   // .container { ... }
  meta: string,   // *.js-meta.xml with apiVersion + targets
}
```

> **Status:** the LWC emitter is marked "Code present, not wired into CLI" in the README status table. Today, call `emitLWC(irModule)` directly from a Node script and write each output to its appropriate file in your component bundle.


## File layout in a Salesforce DX project

For a component named `claimsList`:

```
force-app/main/default/lwc/claimsList/
├── claimsList.html              ← LwcOutput.html
├── claimsList.js                ← LwcOutput.js
├── claimsList.css               ← LwcOutput.css
└── claimsList.js-meta.xml       ← LwcOutput.meta
```

The emitter generates **all four files in one call**, but writing them to disk is your job. The class name in `.js` is PascalCase from the Ion module name — `claims-list` → `ClaimsList`.

Verified per `tests/emit/lwc.test.ts:159-245`.


## HTML template — LWC syntax conventions

LWC uses HTML-like template syntax with these LWC-specific conventions:

- `lwc:if={condition}` / `lwc:else` — conditional rendering (not `v-if` or JSX ternary)
- `for:each={items} for:item="item"` — list iteration
- `{varName}` — dynamic interpolation (curly braces, NOT `${name}` or `{{ name }}`)
- `onclick={handler}` — event handlers (curly braces, NOT `"handler"`)

The LWC emitter handles ALL of these:

### Var refs become `{varName}`

```
App(span, [Str(""), Var("claimTitle")])
```

emits:

```html
<span>{claimTitle}</span>
```

Verified per `tests/emit/lwc.test.ts:145-149`.

### Event handlers — curly braces

```
App(button, [Str("onclick=handleSubmit"), Str("Submit")])
```

emits:

```html
<button onclick={handleSubmit}>Submit</button>
```

NOT `onclick="handleSubmit"`. Verified per the LWC test (`isLwcIdentifier(v)` regex matches `handleSubmit`, so it gets curly braces).

⚠️ **Static string attributes that LOOK like identifiers also get curly braces.**

```
App(div, [Str("class=container")])
```

emits:

```html
<div class={container}>...</div>
```

The emitter's regex (`/^[a-zA-Z_][a-zA-Z0-9_.]*$/`) treats `container` as a JS identifier and binds it to a property named `container` on the LWC class. **This is wrong for static class names** — you wanted `class="container"`. Workaround: use a multi-word value to defeat the regex (`class=container+page` → `class="container page"`, treated as a string).

This is an emit-time gotcha verified by `tests/emit/lwc.test.ts:111-116`. **Either hand-edit, or always use multi-word class values** (even if the second word is a no-op like `class=container+x`).

### `lwc:if` / `lwc:else` from `if/then/else`

Surface syntax is `if cond then a else b` (the `case ... of` form documented in `ion-syntax.md` does NOT parse — the IR-level `Case` node is what the LWC emitter recognises, generated by `if/then/else`):

```ion
let banner = if hasClaims then p([], "Has claims") else p([], "No claims")
```

emits:

```html
<template lwc:if={hasClaims}>
  <p>Has claims</p>
</template>
<template lwc:else>
  <p>No claims</p>
</template>
```

Verified per `tests/emit/lwc.test.ts:125-134`.

### `for:each` iteration

LWC's iteration syntax appears in attribute strings:

```
App(ul, [Str("for:each=claims for:item=claim")])
```

emits:

```html
<ul for:each={claims} for:item={claim}>
  ...
</ul>
```

Both `for:each` and `for:item` correctly bind to identifier values per the test (`tests/emit/lwc.test.ts:151-156`).

⚠️ Without an explicit `key`, LWC will warn at runtime. The emitter doesn't generate `key={claim.id}` automatically — hand-add or include `for:key=claim.id` in the attribute string (untested).


## JS class — LWC class generation rules

The emitter inspects `let` binding names to decide how to emit each:

| Name pattern | Emit shape |
|---|---|
| `recordId`, `accountId`, `*Id` | `@api recordId = '';` (public API field) |
| `getX` (Abs body) | `get x() { ... }` (computed getter, name strips `get` and lowercases first letter) |
| `handleX` (Abs) | `handleX(event) { event.preventDefault(); ... }` (event handler with auto `event.preventDefault()`) |
| Other Abs | `methodName(args) { ... }` |
| Other non-Abs | `@track fieldName;` (reactive field) |

Verified per `tests/emit/lwc.test.ts:159-194`.

### Example — full module

```ion
let recordId = ""
let claims = 0
let getClaimCount = () -> claims

let handleSubmit = () -> "handled"
```

emits in `js`:

```js
import { LightningElement, api, track } from 'lwc';

export default class ClaimsList extends LightningElement {
  @api recordId = '';
  @track claims = 0;
  
  get claimCount() {
    return this.claims;
  }
  
  handleSubmit(event) {
    event.preventDefault();
    return 'handled';
  }
}
```

Imports `LightningElement`, `api`, `track` from `lwc`. The `event.preventDefault()` injection on `handle*` is automatic — useful for form-submit and anchor-click handlers, occasionally unwanted (e.g., for keyboard events). No opt-out today.


## CSS file — placeholder

The emitter always writes a `.container { ... }` placeholder. Verified per the test. There's no surface syntax for CSS in Ion; treat the `.css` output as a stub and hand-fill.


## Meta file — fixed shape

The `.js-meta.xml` is generated as:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>59.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightning__AppPage</target>
        <target>lightning__RecordPage</target>
        <target>lightning__HomePage</target>
    </targets>
</LightningComponentBundle>
```

Verified per `tests/emit/lwc.test.ts:196-209`. The `apiVersion=59.0` and three default targets are hard-coded. To change them, hand-edit the emitted file.


## Worked example — Read-only claims list

```ion
// module: claims-list

let recordId = ""
let claims = ""

let getClaimCount = () -> claims

let app = template([], div("class=container+claims-list",
  if claims then p([], "No claims yet")
  else ul("for:each=claims for:item=claim", li("class=item+x", "claim"))
))

let handleRefresh = () -> ""
```

Expected emits:

**`claims-list.html`:**

```html
<template>
  <div class="container claims-list">
    <template lwc:if={claims}>
      <p>No claims yet</p>
    </template>
    <template lwc:else>
      <ul for:each={claims} for:item={claim}>
        <li class={item}>claim</li>
      </ul>
    </template>
  </div>
</template>
```

(Note `class={item}` not `class="item"` — the static-string identifier gotcha.)

**`claims-list.js`:**

```js
import { LightningElement, api, track } from 'lwc';

export default class ClaimsList extends LightningElement {
  @api recordId = '';
  @track claims = '';
  
  get claimCount() {
    return this.claims;
  }
  
  handleRefresh(event) {
    event.preventDefault();
    return '';
  }
}
```

After emit, hand-fix the `class={item}` → `class="item"` issue and any `event.preventDefault()` you don't want.


## Gap summary — LWC target

| Feature | Status | Workaround |
|---|---|---|
| 4-file structured output | ✅ works | — |
| `lwc:if`/`lwc:else` from two-arm Case | ✅ works | — |
| `for:each`/`for:item` from attribute string | ✅ works | — |
| `{varName}` interpolation for Var refs | ✅ works | — |
| `@api` for `*Id` properties | ✅ works | — |
| `@track` for non-Abs fields | ✅ works | — |
| `get X` getter from `getX` Abs | ✅ works | — |
| `handle*` auto-injects `event.preventDefault()` | ✅ works | — |
| Static `class="foo"` (single-word identifier) | ❌ becomes `class={foo}` | use multi-word value: `class=foo+x` |
| Custom `apiVersion` in meta | ❌ hard-coded `59.0` | hand-edit |
| Custom targets in meta | ❌ hard-coded 3 targets | hand-edit |
| `@wire(...)` decorator for Apex/Data callouts | ❌ no surface | hand-edit |
| `@api` on methods (not just fields) | ❌ no surface | hand-edit |
| `key={item.id}` in `for:each` | ❌ not auto-generated | include `for:key=item.id` (untested) |
| `<lightning-*>` base components | ⚠️ via tag in attribute string (untested) | extend `HTML_TAGS` or use `raw(...)` |
| Event firing (`this.dispatchEvent(...)`) | ❌ no path | hand-write inside method body |
| `connectedCallback`/`disconnectedCallback` lifecycle | ❌ no naming convention | hand-edit |
| CSS content from Ion | ❌ placeholder only | hand-edit |
| `ion build --target lwc` from CLI | ❌ not wired up | call `emitLWC(irModule)` from Node |


## When to use LWC target

- **Read-only display components** — claims list, account dashboard, status badges.
- **Form components with simple submit handlers** — the `handle*` auto-`preventDefault()` is the right call 90% of the time.
- **Components mostly driven by `@api` props** — let the parent wire data in.

## When to NOT use LWC target

- **Wire-decorated components** — `@wire(getRecord, ...)` requires precise decorator emission that's not in scope today.
- **Custom event-firing components** — `this.dispatchEvent(new CustomEvent(...))` patterns need hand-writing.
- **Complex iteration with key attributes** — `key` and stable identity are harder to express than the emitter handles.


## Recommended workflow

1. Sketch the component bundle skeleton in Ion: `recordId`, the data fields (`@track`-shaped), the `get*` getters, and the template structure.
2. Call `emitLWC(irModule)` and write each file to `force-app/main/default/lwc/<bundleName>/`.
3. **Hand-fix the static-string `class={...}` gotcha** before deploying.
4. **Add `@wire`** decorators by hand for any Salesforce data (Apex methods, getRecord, getRelatedListRecords).
5. Run `sfdx force:lightning:lwc:test:run` and `sfdx force:source:deploy` to validate.

The LWC emitter has the **richest naming-convention logic** of any target — once you understand the `getX → get x()`, `handleX → handler with preventDefault`, `*Id → @api` rules, you can produce a substantial component bundle with very little Ion. The 30-second-or-less `single-word class` gotcha is the dominant remaining sharp edge.
